IT 서비스 요청·장애 관리

웹프로그래밍 II · Spring MVC, Spring JDBC, AspectJ, H2, JSP, Tomcat, JUnit 5

대학 정보전산원이 학생과 교직원의 장애 신고와 서비스 요청을 받는다는 설정으로 만들었습니다. 요청 유형, 우선순위, 제목, 내용이 빠지면 항목별로 돌려보냅니다. 통과하면 요청 번호와 접수 시각이 생기고 상태는 접수로 시작합니다.

  • 목록은 10·20·50건 단위로 나누고, 제목·내용·요청자 검색과 상태·유형·우선순위 필터를 붙였습니다.
  • 상태 변경은 접수, 처리 중, 완료만 허용합니다. 값이 이상하거나 사유가 없거나 같은 상태면 거절하고, 바뀐 경우에만 이력을 남깁니다.
  • 서비스 메서드의 인자, 실행 시간, 성공과 오류는 AOP로 콘솔과 로그 테이블에 기록합니다.
  • 회원은 접수자와 관리자로 가입합니다. 접수, 검색, 상세, 상태 변경, 로그는 MockMvc 통합 테스트로 확인했습니다.

배운 점. 화면을 만들기 전에 상태가 몇 개인지, 어떤 변경을 거절할지를 정해야 나중에 이력이 깨지지 않습니다. 테스트는 기능이 되는지보다, 되면 안 되는 입력을 먼저 적는 쪽이 버그를 빨리 보여 줬습니다.

구현 코드가 아니라 설계 문서입니다. 인증, 회원, 알림, 운영, 영화, 예매, 결제, 관람평, 매점으로 경계를 나눴습니다.

  • 실시간 좌석 예매, 예매 취소, 결제와 환불, 상영 전 알림, 멤버십 포인트, 직원 근무처럼 역할이 다른 기능을 명세로 적는 데 참여했습니다.

배운 점. 이름만 비슷해도 결제와 환불, 예매와 취소는 데이터가 다릅니다. 그림을 그리기 전에 누가 어떤 결과를 받는지 문장으로 고정해야 팀 안에서 같은 기능을 두 번 그리지 않습니다.

수업에서 이어서 가져온 것

  • C와 자료구조로 배열, 함수, 반복, 재귀를 먼저 익혔습니다. 계산 순서를 직접 나누는 연습이 나중에 요청 처리 순서를 나눌 때 남았습니다.
  • Java 수업과 연습으로 클래스와 예외를 다뤘고, 데이터베이스 수업에서 SQL, 조인, 저장 함수를 실습했습니다. 웹 과제의 회원과 예약은 이 두 과목이 만나야 동작했습니다.
  • 운영체제와 컴퓨터구조는 이론 과제 중심입니다. 프로세스와 명령 실행을 코드로 만든 프로젝트는 아닙니다.
  • C#은 챕터 실습 수준이고, Flutter는 강의 자료만 있어 포트폴리오 항목에서 빼 두었습니다.
  • 부산도서관 국가근로는 개발 직무는 아닙니다. 공개된 장소에서 시간을 지키고 같은 일을 반복하는 경험으로만 적었습니다. 기간은 이력서에 직접 넣으면 됩니다.

지원 직무와 맞추면

모집 업무는 소프트웨어 기능 설계, 구현, 테스트, 배포, 버전 관리입니다. 위 프로젝트 가운데 요청 관리가 그 다섯 단계에 가장 가깝습니다. 상태를 먼저 정하고, JDBC로 저장하고, 통합 테스트로 거절 케이스를 확인했습니다. 실행 파일은 Maven WAR로 묶어 Tomcat에 올리는 구성입니다. 버전 관리는 수업에서 GitLab으로 실습 소스를 다룬 수준이라, 현업 브랜치 전략은 입사 후 팀 방식을 따르겠습니다.

설비 통신이나 PLC는 다룬 적이 없습니다. 일학습병행에서 그 용어와 기존 제품의 화면부터 익히겠습니다.
